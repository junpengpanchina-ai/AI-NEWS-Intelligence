# PJ Intelligence 路线：Google To C Product OS

观察日期：2026-10-05。本文只重写产品路线。不改现有代码，不新增接口，不新增数据表。

V0.1 的资讯采集和单条研判、V0.2 的 Events / Market Signals 继续按现在的方式运行。它们在新路线里降为辅助层。

## 1. 项目定位

PJ Intelligence 不是新闻看板，而是 Google To C 产品侦察与页面验证系统。

它要回答的问题是：Google 上哪一类面向普通用户的搜索需求，值得做成一个可被检索、可被 AI 答案引擎引用的页面，以及这个页面上线后有没有被验证。

对象是消费者能直接打开的产品页、对比页、替代方案页和问题解答页。企业销售线索、全球新闻大屏、地缘地图都不在这条产品里。

一条资讯、一个事件、一个关键词，都不能单独触发 Build。Build 只从已经审过的 Opportunity Card 开始。

## 2. 主链路

```text
Search Demand
  → Market Signal
  → Keyword Cluster
  → Competitor Page
  → Opportunity Card
  → Page Factory
  → GEO / AEO Audit
  → Validation Review
```

| 阶段 | 它是什么 | 它留下什么 |
| --- | --- | --- |
| Search Demand | 用户在 Google 上实际会搜的 To C 问法：工具、对比、替代、问题、品牌 | 一条需求，带查询词和意图 |
| Market Signal | 需求或竞品正在变化的证据。V0.2 的 Event 属于这一层 | 一条信号，挂到相关需求上 |
| Keyword Cluster | 同一意图下的一组查询，而不是一堆相近标题 | 一个簇：主查询、变体、意图 |
| Competitor Page | 当前在 Google 或 AI 答案里占住这个簇的具体页面 | 页面库中的一页：URL、页面类型、缺口 |
| Opportunity Card | 对“要不要做一页”的决定 | 一张卡：簇、缺口、页面类型、不做的理由或做的条件 |
| Page Factory | 按已通过的卡片生产一页 | 一页草稿或已发布页，追溯到那张卡 |
| GEO / AEO Audit | 这页能否被 AI 答案引擎引用 | 一份审计：分数、缺口、未改动的原文 |
| Validation Review | 这页是否真的接住了原来的搜索需求 | 保留、修改或下线，以及一条可复用的纠正 |

后一阶段只读前一阶段已经落下来的对象。不允许从资讯标题直接跳到页面生产。

## 3. 资讯层的位置

Items / News 只做辅助，不作为 Build 的主依据。

资讯回答的是“外面发生了什么”。主链路回答的是“哪一个 Google To C 查询值得一页，这页有没有站住”。热度高的报道可以成为 Market Signal 的材料，用来说明某个簇为什么现在值得看。它不能代替 Search Demand，也不能代替 Competitor Page。

因此：

- 采集、去重、本地打分、手动单条研判，留在 V0.1。
- 多篇相似资讯收成 Event，留在 V0.2，并改称为 Market Signal 的一种来源。
- 打开页面、刷新、采集、构建事件，继续不调用模型。
- 模型仍只在用户点开某一条资讯或某一个事件、并按下研判时使用。
- 以后的 Keyword Cluster、Competitor Page、Opportunity Card 不从“今日最高分资讯”自动生成。

## 4. 参考模块

这些模块只提供工作方法。不把它们的仓库、脚本或提示词抄进本项目。

### geo-optimizer：GEO / AEO audit

用在 Page Factory 之后。审计对象是已经生成的页面，不是资讯正文。

关注 AI 答案引擎能不能引用这一页：爬虫是否被挡住、`llms.txt` 是否说明这页是什么、结构化数据是否对应页面类型、标题和正文是否对得上查询、文中是否有可核对的数字和来源。输出是 0–100 的分数和一份缺口清单。审计本身不改页面。要改，必须先有一张通过的 Opportunity Card，并且由人确认。

### ai-news-radar：资讯源健康、多源合并、精选/全量

只用在资讯辅助层。

- 每个源要能看出是否还活着、最近抓到多少、最近是否失败。某个源失败不让整次采集失败。
- 同一件事的多源报道先合并，再给人看。V0.2 的 Event 已经是这个方向。
- 默认看精选信号。全量条目只在追查某一个簇时打开，不作为日常主画面。

### AI-Search-Hub：多 AI 搜索入口

用在 Validation Review，用来核对一个查询在不同答案引擎里被谁回答。

按问题选入口，而不是把同一个提示词打到所有引擎。和 Google To C 直接相关的入口是面向全球网页的那一个。需要登录的站点由人自己打开。不复制浏览器配置，不附着到已登录的会话。

### maoxuan-skill：战略审查

用在 Opportunity Card 之前，防止把热闹当成机会。

审查只问三件事：这个簇的主要矛盾是什么（缺的是页面、数据，还是需求本身不存在）；谁是这页要服务的用户，谁不是；证据来自搜索需求和竞品页，还是只来自几篇报道。说不清主要矛盾的簇，不做卡，也不进 Page Factory。

### headcount：部门化 skill 组织

后面的系统按环节调用窄能力，而不是一个总模型包办整条链路。

侦察、聚类、竞品页、卡片、造页、GEO 审计、验证，各自是一块职责。一块只读自己的输入，只写自己的产物。和当前阶段无关的能力不挂进日常操作。V0.8 之前不把这些职责做成对外平台。

### pro-workflow：长期记忆和纠错

用在 Validation Review 之后。

一次验证如果否掉了某类页面，就留下一条短规则：哪一种卡不再做、哪一种证据不够、哪一种页面结构没有被引用。下一次做卡和造页先读这些规则。规则由人确认后才写入。不靠登录系统保存，不在每次打开页面时重写。

## 5. V0.1 到 V0.8

已经落地的两版保持原样。V0.3 起才进入新的主链路，而且每一版只加一个对象。

### V0.1 News Assist

已有。公开源采集、去重、本地打分、用户点击后的单条研判。它是辅助材料库。

### V0.2 Market Signals

已有。把多篇相似资讯收成 Event，本地计算事件热度，用户点击后才研判事件。在新路线里，Event 是 Market Signal，用来提示某个方向可能在动。它仍然不是 Build 指令。

### V0.3 Keyword Clusters

第一个新对象。把 To C 搜索需求收成簇：主查询、变体、意图（工具、对比、替代、问题、品牌）。信号可以挂到簇上，但簇的主键是查询，不是新闻标题。没有查询词的事件，留在信号列表里，不进簇。

### V0.4 Competitor Page Library

为每个簇登记现在占住这个查询的页面：URL、站点、页面类型、它覆盖了什么、缺了什么。库里的一页是侦察对象，不是要复制的模板。没有竞品页的簇可以保留，但要标明“尚未看到对手”，不能直接当成空白机会。

### V0.5 Opportunity Cards

把簇、信号和竞品页收成一张可决定的卡。卡上写明页面类型、要补上的缺口、做的条件，以及不做的理由。人可以退回、搁置或通过。只有通过的卡才能进入下一版。模型可以在人点击后帮助整理卡片，不能批量生成并自动通过。

### V0.6 Page Factory + GEO Audit

Page Factory 只消费已通过的卡，产出一页，并记下它来自哪张卡。页做好之后跑 GEO / AEO 审计，得到分数和缺口。审计失败的页留在草稿，不假装已经可被引用。审计不自动改页。

### V0.7 Validation Review

对照原来的 Search Demand 看这页：查询是否被这页回答、竞品缺口是否还在、AI 答案入口里是否出现这页或同类页。结论只有三种：保留、修改、下线。修改回到 Page Factory；下线写回一条纠正规则，供以后的卡片读取。

### V0.8 Google To C Product OS

把上面八段收成一条可重复的操作系统：从需求进入，到验证离开，中间每段都有自己的对象和负责人。资讯层仍挂在 Market Signal 旁边。到这一版，日常主画面是簇、竞品页、卡片和验证结果。Items / Events 不再占据默认首页。

## 6. 近期不做

下面这些即使做到 V0.8 也不做。它们会把系统拉回新闻台或平台化，偏离 Google To C 页面验证。

- WorldMonitor 式地图
- 全球新闻大屏
- 桌面端
- MCP / SDK
- 自动批量模型分析
- 复杂登录系统

密钥继续只放在环境变量里。采集和刷新继续不调用模型。WorldMonitor 的源码、地图、桌面壳和对外代理层仍然不引入。`docs/worldmonitor_reference.md` 只保留为 V0.2 的架构取舍记录，不作为 V0.3 以后的产品蓝图。
